# แผนทางเทคนิค: จองคิวตรวจสุขภาพ (Booking)

อ้างอิง: `specs/001-booking/spec.md`  
Spec ID: `SPEC-BKG-001`  
สถานะ: Draft  
วันที่: 2569-09-16

## 1. สรุปแนวทาง

ฟีเจอร์นี้ให้ผู้รับบริการที่ยืนยันตัวตนแล้วค้นหาแพ็กเกจ วัน และช่วงเวลาตรวจที่ว่างภายใน 30 วัน (`FR-BKG-01`).
ผู้ใช้เลือกช่วงเวลาและยืนยันการจองได้ไม่เกิน 1 รายการต่อวัน โดยระบบตรวจคิวเดิมและจำนวนที่นั่งซ้ำ ณ เวลายืนยัน (`FR-BKG-02`, `FR-BKG-03`).
ระบบบันทึกการจอง ตัดที่นั่ง และออกหมายเลขคิวให้ผู้ที่ยืนยันก่อน โดยหมายเลขคิวไม่ซ้ำกันภายในวัน (`FR-BKG-04`, `ASM-03`, `ASM-04`).
ระบบส่งข้อความยืนยันแบบ asynchronous และเก็บรายการส่งซ้ำเมื่อการส่งไม่สำเร็จ (`FR-BKG-05`, `IF-NOT-01`, `NFR-REL-02`).
ระบบต้องใช้ข้อมูลผู้รับบริการผ่าน IDP/HIS และบันทึก audit log ตามข้อกำหนดข้อมูลสุขภาพ (`IF-IDP-01`, `IF-HIS-01`, `DOM-PDPA-01`).

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| MySQL | `CON-TECH-01` | ฐานข้อมูลตามมาตรฐานฝ่าย IT ของโรงพยาบาล |
| React (Vite) | **ทีมเลือกเอง ไม่ได้มาจาก spec** | หน้าบ้านสำหรับค้นหาและยืนยันการจอง |
| Python FastAPI | **ทีมเลือกเอง ไม่ได้มาจาก spec** | หลังบ้านสำหรับ API และ business flow |
| กลไก asynchronous notification | `IF-NOT-01` | รายละเอียด queue และ retry ต้องรอคำตอบ `Q-06` |
| TLS 1.2 ขึ้นไป | `NFR-SEC-01` | ใช้กับการรับส่งข้อมูลการจอง |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ |
|---|---|---|
| `booking` | HN, วันตรวจ, แพ็กเกจ, ช่วงเวลา, หมายเลขคิว, สถานะ, เวลาและผู้สร้างรายการ | `FR-BKG-02`, `FR-BKG-04`, `AC-BKG-01`, `AC-BKG-02` |
| `time_slot_capacity` | วันตรวจ, แพ็กเกจหรือเงื่อนไขที่เกี่ยวข้อง, โควตา, จำนวนที่นั่งคงเหลือ | `FR-BKG-01`, `FR-BKG-03`, `FR-BKG-06`, `ASM-01` |
| `notification_delivery` | รหัสการจอง, ช่องทาง SMS/LINE, สถานะการส่ง, เวลา retry ครั้งถัดไป | `FR-BKG-05`, `NFR-REL-02`, `IF-NOT-01` |
| `audit_log` | ผู้เข้าถึง, เวลา, รหัสผู้รับบริการ, เหตุการณ์การเข้าถึง | `DOM-PDPA-01`, `AC-BKG-06` |

ข้อจำกัดข้อมูล:

- `booking` ต้องอ้างอิงผู้รับบริการด้วย HN และ **ไม่มีฟิลด์เลขบัตรประชาชน** ตาม `IF-HIS-01`.
- เลขบัตรประชาชนใช้ค้นหาใน HIS ตาม `IF-HIS-01` แต่ไม่เก็บในตารางการจอง.
- รายละเอียดฟิลด์แพ็กเกจ สถานะคิว และ notification ต้องรอคำตอบ `Q-03`, `Q-05` และ `Q-06`.

## 4. API / หน้าจอ

| รายการ | Input / Output หลัก | รองรับ |
|---|---|---|
| `GET /booking/slots` | Input: วันและแพ็กเกจ; Output: ช่วงเวลาว่างและจำนวนที่นั่งคงเหลือภายใน 30 วัน | `FR-BKG-01`, `AC-BKG-05` |
| `GET /booking/slots?package=` | Input: แพ็กเกจใหม่; Output: ช่วงเวลาว่างที่คำนวณใหม่ | `FR-BKG-06` |
| `POST /booking/validate` | Input: HN, วัน, แพ็กเกจ, ช่วงเวลา; Output: ผลตรวจคิวเดิมและที่นั่งล่าสุด | `FR-BKG-02`, `FR-BKG-03` |
| `POST /booking` | Input: HN, วัน, แพ็กเกจ, ช่วงเวลา; Output: ผลจองและหมายเลขคิว | `FR-BKG-04`, `AC-BKG-01`, `AC-BKG-03` |
| `GET /booking/{booking_id}` | Input: รหัสการจอง; Output: รายละเอียดการจองและหมายเลขคิว | `FR-BKG-02`, `FR-BKG-05` |
| `POST /notification-deliveries` | Input: รหัสการจองและช่องทาง SMS/LINE; Output: สถานะรับคำขอแบบ asynchronous | `FR-BKG-05`, `IF-NOT-01` |
| หน้าค้นหาและเลือกช่วงเวลา | Input: แพ็กเกจและวัน; Output: รายการช่วงเวลา/ที่นั่งคงเหลือ | `FR-BKG-01`, `FR-BKG-06` |
| หน้ายืนยันและผลการจอง | Input: การยืนยัน; Output: ข้อผิดพลาดช่วงเวลาเต็ม, ตัวเลือกใกล้เคียง 3 รายการ หรือหมายเลขคิว | `FR-BKG-03`, `FR-BKG-04`, `FR-BKG-05` |

รายละเอียด error response และเกณฑ์ “ยืนยันก่อน” ยังต้องรอคำตอบ `Q-04`, `Q-05`, `Q-06` และ `Q-07`.

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| `CON-TECH-01` | ตารางเทคโนโลยีและโมเดลข้อมูลใช้ MySQL | ใช้แล้ว |
| `DOM-PDPA-01` | Entity `audit_log`, API/flow การเข้าถึงข้อมูล และ `AC-BKG-06` | ใช้แล้ว |
| `IF-IDP-01` | Flow ตรวจผลยืนยันตัวตนก่อนเรียกข้อมูลผู้รับบริการ | ใช้แล้ว |

| `IF-NOT-01` | `POST /notification-deliveries` และการส่งข้อความแบบ asynchronous | ใช้แล้ว |

## 7. ลำดับงาน

1. ตอบ `Q-01`, `Q-03` ถึง `Q-08` และบันทึกคำตอบลง `spec.md` ก่อน implementation.
2. กำหนดโมเดลข้อมูล `booking`, `time_slot_capacity`, `notification_delivery` และ `audit_log` ตาม `FR-BKG-01` ถึง `FR-BKG-06` และ Constraints.
3. สร้าง flow IDP/HIS และ audit log ตาม `IF-IDP-01`, `IF-HIS-01`, `DOM-PDPA-01`.
4. สร้างหน้าค้นหาและ API ช่วงเวลาว่าง รองรับ `FR-BKG-01`, `FR-BKG-06` และ `AC-BKG-05`.
5. สร้างการตรวจคิวซ้ำและการยืนยันแบบให้ผู้ยืนยันก่อนมีสิทธิ์ รองรับ `FR-BKG-02`, `FR-BKG-03`, `FR-BKG-04`, `ASM-02`, `ASM-03`, `ASM-04`.
6. สร้าง asynchronous notification และ retry รองรับ `FR-BKG-05`, `IF-NOT-01`, `NFR-REL-02` และ `AC-BKG-04`.
7. เพิ่ม TLS 1.2 ขึ้นไปและตรวจการไม่เก็บเลขบัตรประชาชนตาม `NFR-SEC-01` และ `IF-HIS-01`.
8. รัน test `AC-BKG-01` ถึง `AC-BKG-06`, ตรวจ `NFR-USE-01` และตรวจ traceability ก่อนส่งมอบ.

## 8. สิ่งที่ยังไม่ทำ

ส่วนที่เกี่ยวข้องกับแต่ละข้อจะยังไม่สร้างจนกว่าจะได้คำตอบ:

- `Q-01` "ช่วงเวลาใกล้เคียง" นับเฉพาะวันเดียวกัน หรือรวมวันถัดไปด้วย? -> ถามพยาบาลคัดกรอง
- `Q-03` แพ็กเกจมีผลต่อช่วงเวลาว่างและจำนวนที่นั่งอย่างไร และเมื่อเปลี่ยนแพ็กเกจต้องโหลดข้อมูลใหม่จากแหล่งใด? -> ถามผู้ดูแลตารางตรวจ / ทีม UC-09
- `Q-04` ช่วงเวลาใกล้เคียง 3 ตัวเลือกต้องคัดเลือกและเรียงลำดับด้วยเกณฑ์ใด และอนุญาตให้ข้ามไปวันอื่นได้หรือไม่? -> ถามพยาบาลคัดกรอง / ทีมเอง
- `Q-05` "คิวที่ยังไม่ได้ใช้" หมายถึงสถานะใดบ้าง และการตรวจว่าจองซ้ำในวันเดียวกันต้องพิจารณาแพ็กเกจหรือเฉพาะวันที่? -> ถามเจ้าหน้าที่เวชระเบียน
- `Q-06` เมื่อระบบ SMS/LINE ไม่ตอบสนอง ระบบต้องรอนานเท่าใดก่อนถือว่าส่งไม่สำเร็จ และต้อง retry กี่ครั้งหรือจนถึงสถานะใด? -> ถามทีมระบบแจ้งเตือน / ทีมเอง
- `Q-07` หากระบบยืนยันตัวตนหรือ HIS ไม่ตอบสนอง หรือค้นผู้รับบริการด้วยเลขบัตรประชาชนไม่พบ ระบบต้องแสดงผลและหยุดขั้นตอนอย่างไร? -> ถามผู้ดูแลระบบยืนยันตัวตน / เจ้าหน้าที่เวชระเบียน
- `Q-08` การวัดเวลา "จองสำเร็จภายใน 3 นาที" เริ่มและสิ้นสุดที่เหตุการณ์ใด และต้องครอบคลุมผู้ใช้ประเภทใด? -> ถามทีมเอง / ผู้แทนผู้ใช้งาน
